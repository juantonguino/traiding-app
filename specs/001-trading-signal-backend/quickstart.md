# Quickstart: Trading Signal Backend

**Branch**: `001-trading-signal-backend` | **Date**: 2026-08-14 | **Spec**: [spec.md](spec.md) | **API**: [contracts/api.md](contracts/api.md) | **Data model**: [data-model.md](data-model.md)

This is a **validation / run guide**. It does not contain full implementation code; details live
in the linked contracts and data model, and tasks are generated by `/speckit.tasks`.

Prerequisites: Docker Desktop (or Docker Engine) with Compose v2, JDK 21, and the project's
Gradle wrapper (`./gradlew`).

## 1. Configure environment variables

Create a local `.env` (never committed) from `.env.example`:

```bash
cp .env.example .env
```

Fill in at minimum:

```text
TELEGRAM_BOT_TOKEN=   # your bot token (empty/placeholder disables sending)
TELEGRAM_CHAT_ID=     # your chat id
```

Defaults in `application.yml` (safe by default): `TRADING_MODE=PAPER`,
`MAX_OPEN_TRADES=1`, `ALLOW_REAL_ORDERS=false`, plus symbols/interval/strategy parameters.
The application refuses to start if `TRADING_MODE != PAPER`, `MAX_OPEN_TRADES != 1`, or
`ALLOW_REAL_ORDERS = true`.

## 2. Start MySQL and the application with Docker Compose

```bash
docker compose up --build
```

- Starts `mysql:8.4` with a persistent volume and healthcheck.
- The app service depends on MySQL being healthy, then starts the Spring Boot app.
- Flyway runs automatically at startup (migrations in `src/main/resources/db/migration`).

## 3. Run migrations

Automatic on startup. To inspect/verify manually:

```bash
docker compose exec mysql mysql -u trading -ptrading trading_bot -e "SHOW TABLES;"
docker compose logs app | grep -i flyway
```

## 4. Configure symbols and interval

Via environment variables (see `.env.example`):

```text
TRADING_SYMBOLS=BTCUSDT,ETHUSDT
TRADING_TIMEFRAME=15m
TRADING_STRATEGY=sma-rsi
```

Restart the app after changes (`docker compose restart app`).

## 5. Configure Telegram

Set `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` in `.env`. If either is empty, the adapter logs a
warning and notifications are skipped (analysis is never blocked). Every message includes
`PAPER TRADING`.

## 6. Verify health check

```bash
curl http://localhost:8080/api/v1/health
```

Expect:

```json
{ "status": "UP", "checks": { "mysql": "UP", "binance": "UP", "telegram": "UP" } }
```

## 7. Check Binance data reception

```bash
curl http://localhost:8080/api/v1/status
```

- `marketDataHealthy` becomes `true` after the first closed candle is processed.
- `lastCandleProcessedAt` advances as candles close.
- If `marketDataHealthy` stays `false`, check `docker compose logs app` for WebSocket reconnect logs.

## 8. Run a signal test

Signals are generated automatically from closed candles. Confirm with:

```bash
curl "http://localhost:8080/api/v1/signals?symbol=BTCUSDT"
```

Expect a non-empty `items` array with BUY/SELL/HOLD rows (status `GENERATED`/`ACCEPTED`/`IGNORED`).
You can also verify the unit path directly:

```bash
./gradlew test --tests "*SignalGeneration*"
```

## 9. Verify the single-open-trade rule

1. Let a BUY open a trade: `curl http://localhost:8080/api/v1/trades/open` shows the open trade.
2. Any later BUY while it is open must be recorded as `IGNORED` with
   `ignoreReason = GLOBAL_TRADE_ALREADY_OPEN` (check `/api/v1/signals?status=IGNORED`).
3. Concurrency proof (automated): `./gradlew test --tests "*Concurrency*"` fires two simultaneous
   BUY signals and asserts at most one OPEN trade exists.

## 10. Consult a simulated trade's result

After a close (SELL signal, stop-loss, take-profit, manual close, or emergency):

```bash
curl http://localhost:8080/api/v1/trades
curl http://localhost:8080/api/v1/statistics
```

Closed trades include `grossPnl`, `fees`, `slippageCost`, `netPnl`, `returnPct`, and `result`
(`WIN`/`LOSS`/`BREAK_EVEN`), fully reconstructable from stored data.

## End-to-end validation scenarios

1. **Signal → open → close → stats**: wait for a BUY, confirm open trade, trigger a close,
   confirm the closed trade result and updated statistics.
2. **Single-open-trade**: open one trade, attempt another BUY, confirm ignore + notification.
3. **Restart recovery**: open a trade, restart the app, confirm `/api/v1/trades/open` still shows it.
4. **Telegram failure tolerance**: set an invalid token, confirm signals/trades still processed and
   errors are logged without the token.

### Validation record (T071, 2026-08-15)

Run against `mysql:8.4` (Docker Compose) + app on port `8081` (default profile):

- `GET /api/v1/health` → `{"status":"UP","checks":{"binance":"UP","db":"UP","mysql":"UP","telegram":"UP",...}}`.
- `GET /api/v1/status` → `PAPER`, `signalsEnabled=true`, `emergencyActive=false`, open trade reported.
- `POST /api/v1/control/signals/disable|enable` → records `signalsDisabledBy`/`signalsDisabledAt`.
- `POST /api/v1/trades/open/close` with no open trade → `404 NO_OPEN_TRADE` (error DTO with `requestId`).
- **Restart recovery**: seeded an OPEN trade in MySQL, restarted the app, `GET /api/v1/trades/open`
  still returned it (`status=OPEN`, `openSignalId` preserved).
- **Signal → close → stats**: emergency-stop closed the seeded trade (`EMERGENCY_STOPPED`,
  `closedTradeId`), `GET /api/v1/trades` returned the CLOSED trade with `grossPnl`, `fees`,
  `slippageCost`, `netPnl`, `returnPct`, `result=WIN` (exit price fetched live from Binance REST),
  and `GET /api/v1/statistics` returned `closedTrades=1`, `winRatePct=100.00`, and buckets by
  symbol/strategy/timeframe.
- Live Binance WebSocket data reception and signal generation require external connectivity and a
  closed candle; those flows are covered by the automated integration tests
  (`KlineListenerIntegrationTest`, `Concurrency*`).
